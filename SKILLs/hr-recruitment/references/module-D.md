## Positioning

Module D is the **需求理解层 (Requirement Understanding Layer)**. JD 往往由 HR 或业务部门以标准化语言撰写，无法完整传达岗位的真实需求。Module D 通过 LLM 推理分析，对 JD 进行逐条解构，结合用人部门的补充信息，生成一份经过 HR 验证的综合岗位需求文档。

**Module D 解决的核心问题：**

1. **HR 不完全理解 JD**：技术岗 JD 中的专业术语、技能要求，HR 未必清楚哪些是核心哪些是锦上添花。Skill 用推理能力帮助 HR 分辨。
2. **JD 写得太笼统或太理想化**：很多 JD 是"许愿清单"，把所有可能需要的能力全列上去。Skill 帮助区分真正的刚需和过度要求。
3. **等效替代被忽略**：JD 写"熟悉 Python"，但实际岗位需要的是数据处理能力，R/SQL 也可以。Skill 识别底层能力并找到替代方案，扩大候选人池。
4. **用人部门的隐性偏好未被表达**：主管的背景、团队构成、业务方向都暗含招聘偏好，但这些不会写进 JD。Skill 从补充材料中推理这些隐性需求。

**输出物：`comprehensive-requirements.md`** 是 Module D 的核心产出。下游模块优先读取此文件：
- Module A (A-S5)：用于更精准的误分类检测
- Module B (B-S2)：作为基线，分析实际反馈与需求的偏差
- Module C (C-S1)：作为主要条件来源，比原始 jd.md 信息更丰富、更结构化

**向后兼容**：如果 Module D 未运行（comprehensive-requirements.md 不存在），下游模块退回到读取原始 jd.md，行为与之前完全一致。

## Prerequisites

- **jd.md 必须存在**。如果不存在，先让 HR 提供 JD 文本。
- **不依赖其他 Module**。Module D 可以在 A/B/C 之前运行，也可以在任何时候运行。
- **可重复运行**。如果 JD 更新或补充了新材料，可以重新运行 Module D，更新 comprehensive-requirements.md。

## D-S0: 行业/岗位背景简介

### 目标

在开始解析 JD 之前，先由 LLM 基于自身知识，向 HR 简要介绍该类岗位的行业背景。目的是：

1. **帮助 HR 建立认知框架**：尤其是技术类岗位，HR 未必了解岗位的日常工作是什么、哪些技能真正重要
2. **解释 JD 中的专业术语**：提前解释，避免 HR 在后续确认环节因看不懂而随意确认
3. **设定合理预期**：介绍该类岗位当前市场上的候选人分布、典型背景、薪资段位等常识
4. **主动提问**：了解 HR 对这个岗位的已有认知程度，以便调整讲解深度

### 执行步骤

**Step 1：读取 jd.md，判断岗位类型（见 D-S1 Step 1）**

快速读取 JD，判断：招聘类型（实习/校招/社招）+ 岗位性质（技术研发/产品/运营/市场/管理/职能/创意）。

**Step 2：生成行业/岗位背景简介**

基于判断结果，从 LLM 知识库中提取相关背景，向 HR 展示以下内容：

```markdown
## 📋 岗位背景简介 — {岗位名称}

### 这是一个什么样的岗位？
{1-2 句话描述岗位的核心工作是什么，用非专业人士也能理解的语言}

### 在行业中的位置
{这类岗位在公司/行业中扮演什么角色？通常向谁汇报？团队规模一般多大？}

### 候选人通常具备什么背景？
{典型的学历背景、工作经历、技术栈/工具偏好，分校招/社招分别说明}

### JD 中需要特别关注的专业术语
{列出 JD 中 HR 可能不熟悉的专业词汇，逐条简单解释}
示例：
- **{术语A}**：{简单解释，一句话}
- **{术语B}**：{简单解释}
- ...

### 该类岗位的常见"刚性要求" vs "锦上添花"
{基于 LLM 对该类岗位的了解，提前告知哪些技能在行业里是普遍硬性要求，哪些通常只是加分}
示例：
- 通常是刚需：{技能/经验A}、{技能/经验B}
- 通常是加分项：{技能/经验X}、{技能/经验Y}
- 需要根据具体岗位判断：{技能Z}（取决于公司规模/业务阶段）

### 当前市场行情参考
{该类岗位目前市场上的大致供需状况，候选人是否好找，薪资区间参考}
（注：仅供参考，以 HR 实际经验为准）
```

**Step 3：询问 HR 对该岗位的已有认知**

在展示简介后，询问：

> "以上是这类岗位的基本背景介绍。在我们开始详细分析 JD 之前，有几个问题想先了解一下：
>
> 1. 你对这个岗位的日常工作已经有多少了解？是否有过招聘这类候选人的经验？
> 2. 你们团队/业务对这个岗位有什么特殊的背景或需求，是 JD 上没写出来的？
> 3. 有没有你特别困惑或想先确认的地方？
>
> 了解这些可以帮我在后续分析中更有针对性。"

**Step 4：根据 HR 反馈调整深度，然后进入 D-S1**

- 如果 HR 表示已经很了解这个岗位 → 简化后续讲解，直接进入 D-S1 分析
- 如果 HR 表示不太熟悉 → 在 D-S1 的每条分析中附加更详细的解释
- 记录 HR 补充的业务背景信息，在后续步骤中纳入考量

### D-S0 注意事项

- **不要照本宣科**：根据具体 JD 内容定制简介，而非套用通用模板
- **语言要平实**：面向 HR 而非技术人员，避免堆砌术语
- **长度适中**：简介不超过 500 字，重点突出。宁可后续分析中补充，也不要在这里铺陈过长
- **不做价值判断**：不说"这是个好岗位"或"这个 JD 写得不好"，保持中立描述
- **市场信息有时效限制**：明确告知 HR，LLM 知识有截止日期，市场行情仅供参考

### D-S0 Completion

- 向 HR 展示行业/岗位背景简介
- 记录 HR 反馈的业务背景补充信息（用于后续步骤）
- Append to D.log.md: 岗位类型判定结果、HR 对岗位的熟悉程度（高/中/低）
- 进入 D-S1

## D-S1: JD 智能解析

### 目标

对 jd.md 中的每一条要求进行推理分析，判断其优先级和可替代性，输出结构化的 JD 分析报告。

### Step 1: 岗位类型判定

读取 jd.md 后，首先判断岗位类型。岗位类型直接影响后续每条要求的分类逻辑。

**招聘类型（三选一）：**

| 类型 | 判断依据 |
|------|----------|
| **实习生** | 出现"实习""intern""在校生""每周X天"等关键词 |
| **校招应届生** | 出现"应届""校招""202X届""毕业时间"等关键词 |
| **社招** | 出现"X年经验""senior""资深""管理经验"等关键词，或无实习/校招标记 |

**岗位性质（多选，可叠加）：**

| 性质 | 判断依据 |
|------|----------|
| **技术研发** | 涉及编程语言、系统架构、算法、开发框架等 |
| **产品** | 涉及需求分析、用户研究、PRD、产品规划 |
| **运营** | 涉及用户运营、内容运营、活动策划、数据运营 |
| **市场推广** | 涉及渠道推广、品牌营销、媒体投放、Growth |
| **管理岗** | 涉及团队管理、绩效考核、部门规划、P&L |
| **职能支持** | 涉及行政、财务、法务、人力资源等 |
| **创意设计** | 涉及视觉设计、UI/UX、文案创意、视频制作 |

**在分析报告开头即写明岗位类型判定结果及依据，供 HR 确认。**

### Step 2: 逐条解析 JD 要求

对 JD 中的每一条要求或描述，进行四级分类：

#### 分类体系

| 分类 | 定义 | Module C 中的映射 |
|------|------|------------------|
| **🔴 刚需 (Must-have)** | 缺失此项则候选人无法胜任岗位核心工作。不可降级、不可替代。 | 硬性过滤条件（不满足 = 淘汰） |
| **🟡 等效替代 (Substitutable)** | JD 写了具体项，但底层需求可被其他方案满足。列出替代方案组。 | 硬性过滤但以"组"为单位（组内 OR 逻辑） |
| **🔵 次要 (Secondary)** | 有则更好，缺失不影响核心工作，但会影响效率或成长空间。 | 软性评分（权重中） |
| **⚪ 加分项 (Bonus)** | 锦上添花，能区分优秀候选人和普通候选人，但不影响基本胜任。 | 软性评分（权重低） |

#### 岗位类型对分类的影响（关键推理规则）

**同一句 JD 描述，在不同岗位类型下分类可能完全不同。** 以下是核心推理规则：

**实习生岗位：**
- 实习的核心价值是学习和成长，因此对"已掌握XX技能"的要求应普遍降级
- "熟悉XX工具" → 通常降级为 **加分项**（实习就是来学的），除非该工具是日常工作的唯一手段
- "XX经验" → 降级为 **次要** 或 **加分项**（无经验的实习生本就是常态）
- **刚需聚焦在**：学历/在读状态、到岗时间、工作地点、实习时长等硬性约束
- **真正的刚需技能极少**：通常只有"基本的XX能力"才是刚需（如市场岗的基本文案能力）
- 学习能力、主动性、好奇心等软素质在实习场景下比硬技能更重要 → 如果 JD 提到，应提升为 **次要** 而非加分项

**校招应届生岗位：**
- 比实习生严格，但仍以潜力为主、经验为辅
- "X年经验" → 不适用于校招，但可等效替代为"有X段实习经历"或"有相关项目经验"
- "熟悉XX" → 取决于岗位性质：技术岗的核心技术栈可能是 **刚需**，非核心是 **次要**
- 学校/学历要求 → 通常是 **刚需**（校招对学历敏感）
- **特别注意**：校招 JD 经常把"理想候选人画像"写成"岗位要求"，需要区分

**社招岗位：**
- 以实际能力和经验为主要评判标准
- "X年经验" → 通常是 **刚需** 或 **等效替代**（经验年限可被项目深度替代）
- "管理X人团队" → 管理岗是 **刚需**，技术岗是 **加分项**
- 行业经验 → 取决于岗位专业性：金融/医疗等强监管行业是 **刚需**，互联网等快速行业是 **次要**
- **等效替代在社招中最有价值**：很多 JD 用具体工具代替底层能力，需要识别

**技术岗特别规则：**
- 核心技术栈（JD 中反复出现或明确标注的）→ **刚需** 或 **等效替代**
- 周边技术栈（出现一次、写在"优先"/"加分"后面的）→ **次要** 或 **加分项**
- "精通XX"与"了解XX"的措辞差异很重要，前者通常更接近刚需
- 算法/系统设计能力 → 取决于岗位层级，高级岗位是刚需

**管理岗特别规则：**
- 团队管理经验 → **刚需**（无法通过其他方式替代）
- 行业背景 → 通常是 **刚需**（管理岗需要行业判断力）
- 沟通/协调/向上管理 → **刚需**（管理的核心职责）
- 技术深度 → 取决于"技术管理"还是"纯管理"，前者是刚需，后者是次要

**职能/运营/市场岗特别规则：**
- 具体工具（Excel/PS/Tableau 等）→ 通常是 **等效替代**（同类工具可替代）
- 沟通协调能力 → 通常是 **刚需**（面向内外部协作）
- 行业知识 → 取决于专业深度，大多数情况是 **次要**

### Step 3: 等效替代深度分析

对于每个被分类为"等效替代"的条目，**必须**提供以下完整分析框架：

```
### 🟡 等效替代组 #{N}: {底层能力名称}

**JD 原文**: "{JD 中的原始描述}"
**底层能力需求**: {这条要求实际测试的是什么能力？}
**岗位类型影响**: {当前岗位类型下，这条要求的特殊考量}

**可接受方案（满足任一即可）：**
1. {方案A — JD 原文要求} — {说明}
2. {方案B} — {说明为什么可以替代}
3. {方案C} — {说明}

**不可替代场景**: {什么情况下只有原始要求才行}
**替代条件**: {在什么前提下替代方案才成立}
**置信度**: {高/中/低} — {置信度说明}
```

**等效替代分析的质量标准：**
1. 替代方案必须是真实可行的，不能为了凑数而列出不合理的替代
2. 要考虑岗位日常工作的实际场景，不能脱离实际
3. 不可替代场景的判断要准确，避免过度扩大替代范围
4. 置信度反映分析的确定性：如果需要了解岗位日常工作才能判断，应标注"中"或"低"

### Step 4: 隐含需求推理

除了 JD 明文写的内容，推理出 JD **没有写但逻辑上必须的**需求：

| 推理类型 | 示例 |
|---------|------|
| **地理约束** | JD 写"XX研发中心" → 隐含需要能到该城市工作 |
| **时间约束** | JD 写"尽快到岗" → 隐含不接受长 notice period |
| **行业常识** | JD 是金融科技公司的后端岗 → 隐含需要了解基本的金融合规 |
| **团队协作** | JD 职责涉及"跨部门沟通" → 隐含需要良好的沟通能力 |
| **软素质** | JD 描述高压环境 → 隐含需要抗压能力和时间管理 |

**隐含需求也需要分类**（刚需/次要/加分），并标明"推理"来源。

### Step 5: 不确定标注

对于分析过程中不确定的分类，**必须明确标注**而非随意选择一个分类。标注格式：

```
⚠️ 不确定: {条目描述}
当前倾向分类: {刚需/等效替代/次要/加分}
不确定原因: {具体原因，如"不了解岗位日常工作是否需要直接写代码"}
需要 HR 确认: {具体要确认什么}
```

不确定的常见场景：
- JD 用词模糊（"相关经验"——多相关才算？）
- 技能需求的深度不明（"熟悉 SQL"——是写查询还是优化数据库？）
- 岗位定位不清（这是个纯执行岗还是需要独立思考的岗？）

## D-S2: HR 确认 JD 分析

### 交互流程

将 D-S1 的分析结果**分段**展示给 HR（不要一次性输出全部，容易信息过载）：

**第一轮：确认岗位类型判定**
- 展示岗位类型判定结果及依据
- HR 确认或纠正
- 如果岗位类型判定有误，后续分类可能需要全部调整

**第二轮：确认刚需条件**
- 展示所有被分类为"刚需"的条目及推理
- HR 逐条确认：是否真的是刚需？有没有遗漏的刚需？
- 这一轮最关键，因为刚需直接决定 Module C 的硬性过滤

**第三轮：确认等效替代**
- 展示所有等效替代组
- HR 确认：底层能力识别是否准确？替代方案是否合理？
- HR 可以删除不合理的替代方案、添加新的替代方案

**第四轮：确认次要 + 加分项 + 不确定项**
- 展示剩余分类
- 重点关注"不确定"项，请 HR 做出最终判定
- HR 可以调整任何条目的分类

**第五轮：补充**
- 问 HR："还有没有 JD 上没写但你觉得重要的条件？"
- 记录 HR 补充的条件，同样进行分类

### HR 可执行的操作

| 操作 | 效果 |
|------|------|
| **确认** | 分类和描述保持原样 |
| **调整分类** | 改变优先级（如从次要调为刚需）|
| **修改描述** | 细化或修正条件的表述 |
| **补充说明** | 添加额外上下文（如"这个技能是因为我们项目用到"）|
| **删除** | 该条目不是真正的要求 |
| **新增** | 添加 JD 中未提及的新条件 |

### 确认记录

每条修改都要记录**原始分析 → HR 调整**的变更，以便追溯。

### D-S2 Output

Write to `D-analysis/jd-analysis-confirmed.md`。See file-formats.md for template.

### D-S2 Completion

- Write jd-analysis-confirmed.md
- Append to D.log.md: 确认数、调整数、新增数、删除数
- 进入 D-S3 前询问 HR 是否有补充材料

## D-S3: 用人部门上下文理解

### 触发条件

D-S2 完成后，向 HR 询问：

> "JD 分析已完成。你还有用人部门的额外背景资料吗？这些信息可以帮助我推理出 JD 之外的隐藏需求。
>
> 可能有用的资料包括：
> - 面试官/用人主管的简历或背景介绍
> - 团队现有成员的构成信息
> - 部门业务方向说明
> - 主管的用人偏好（口头描述也可以）
> - 历史招聘中的选人倾向
>
> 如果有文件，可以放入 context/ 目录；也可以直接在对话中描述。
> 如果没有，我们直接进入下一步。"

**如果 HR 表示没有 → 跳过 D-S3，直接进入 D-S4。**

**如果 HR 以对话形式提供背景（而非文件）：**
直接基于对话内容进行推理分析，在 hiring-context-analysis.md 中将材料来源注明为 `HR对话描述（{日期}）`，无需将对话内容写入 context/ 目录。

### 材料分析框架

#### 类型 1: 面试官/主管简历

这是最有推理价值的材料。主管的背景深刻影响其用人偏好。

**分析维度：**

| 维度 | 推理方向 |
|------|---------|
| **教育背景** | 名校出身的主管可能更看重学校背景；也可能因为自身优秀而对学历更包容 |
| **职业路径** | 大厂出身可能偏好大厂经验；创业背景可能更看重实干能力 |
| **技术栈** | 主管擅长的技术栈可能成为隐性加分项 |
| **管理风格推断** | 从职业轨迹推断是偏 hands-on 还是偏授权型，影响对候选人独立性的要求 |
| **行业经验** | 主管的行业背景可能影响对候选人行业经验的看重程度 |

**推理原则——必须生成双向假设：**

对于每个推理，**同时提出"偏好相似"和"偏好互补"两个方向的假设**，让 HR 判断。

```
### 面试官分析: {姓名}

#### 教育背景推理
- 面试官学历: {清华 CS 本科 + Stanford MS}
- 假设A (偏好相似): 可能更认可名校背景，因为在自身经历中验证了名校培养质量
- 假设B (偏好互补/中立): 可能对学历更包容，因为自身能力强所以更看重实际能力
- 置信度: 低（仅基于简历推断）
- 需要 HR 确认: 该主管过去面试中是否表现出明显的学校偏好？

#### 技术偏好推理
- 面试官技术栈: {Python, TensorFlow, 分布式系统}
- 推理: 候选人如果有相似技术栈，入职后更容易与主管交流和获得指导
- 转化为偏好: 熟悉 Python + ML 框架可作为加分项
- 置信度: 中
```

**绝对禁止的推理：**
- 不得从姓名/性别推断任何用人偏好
- 不得从年龄推断对候选人年龄的偏好
- 不得做任何可能构成就业歧视的推理
- **性别和年龄相关的推理结果一律不纳入 hiring-context-analysis.md 和 comprehensive-requirements.md**，无论材料中是否有相关信号，也不向 HR 提及（除非 HR 明确在对话中说明有此类要求）

#### 类型 2: 团队现有构成

**分析维度：**

| 维度 | 推理方向 |
|------|---------|
| **技能分布** | 团队缺什么技能 → 可能更需要该技能的候选人 |
| **资历分布** | 全是 senior → 可能需要 junior 做执行；全是 junior → 可能需要能带人的 |
| **背景多样性** | 团队同质化 → 可能需要不同背景增加视角 |
| **规模** | 小团队 → 需要多面手；大团队 → 可以招专才 |

```
### 团队构成分析

#### 技能缺口推理
- 现有团队: {3名后端, 1名前端, 0名数据}
- 推理: 团队缺乏数据分析能力，候选人如果有数据技能是强加分
- 置信度: 中（假设团队有数据需求，但不确定）
- 需要 HR 确认: 团队日常工作是否涉及数据分析？

#### 资历结构推理
- 现有团队资历: {1名 P7, 2名 P6, 1名 P5}
- 推理: 团队结构较均衡，新人可能定位在 P5-P6，需要能独立干活
- 转化为要求: "独立完成任务的能力"可从次要提升为刚需
- 置信度: 中
```

#### 类型 3: 业务方向说明

**分析维度：**

| 维度 | 推理方向 |
|------|---------|
| **业务阶段** | 0→1（需要创新型人才）vs 1→10（需要执行型人才）vs 成熟（需要优化型人才） |
| **扩展方向** | 出海 → 需要语言/跨文化能力；下沉 → 需要接地气的思维 |
| **关键挑战** | 业务面临的核心挑战 → 候选人是否能直接解决 |
| **业务节奏** | 快速迭代 vs 长线打磨 → 影响对候选人工作风格的要求 |

#### 类型 4: 主管口头偏好 / 历史选人倾向

直接从 HR 口述中提取结构化信息：

- **明确偏好**：主管说"我想要XX样的人" → 直接记录
- **隐含偏好**：主管描述理想候选人时的用词倾向 → 推理背后的真实需求
- **历史模式**：过去招了什么人 / 淘汰了什么人 → 行为反映真实偏好

### 推理质量要求

1. **每条推理必须有明确依据**——不能凭空猜测
2. **置信度标注必须诚实**——证据不足就标"低"，不要虚高
3. **双向假设**——避免单向推断导致确认偏误
4. **标注"需要 HR 确认"**——技能的推理只是假设，HR 的确认才是定论
5. **风险标注**——如果推理出的偏好可能不合理（如过度看重学校、潜在年龄偏见），温和提醒

### HR 确认

将所有推理结果展示给 HR，HR 对每条：
- **确认**：推理合理，采纳为用人偏好
- **否认**：推理不准确，不采纳
- **调整**：方向对但需修正细节
- **补充**：HR 根据推理启发，想到了其他偏好

### D-S3 Output

Write to `D-analysis/hiring-context-analysis.md`。See file-formats.md for template.

### D-S3 Completion

- Write hiring-context-analysis.md
- Append to D.log.md: 材料类型、推理条目数、各置信度分布

## D-S4: 综合岗位需求确认

### 目标

将 D-S2（JD 确认分析）和 D-S3（上下文推理，可选）的结果合并为一份结构化的综合岗位需求文档，作为下游 Module A/B/C 的增强输入。

### 合并规则

| 来源 | 优先级 | 说明 |
|------|--------|------|
| HR 在 D-S2 中的确认/修改 | 最高 | HR 的明确判断覆盖一切 |
| D-S3 中 HR 确认的推理 | 高 | 经过 HR 确认的推理等同于 HR 规则 |
| D-S1 原始分析（HR 未修改部分） | 中 | 未被 HR 调整的分析保持原样 |
| D-S3 中 HR 未确认的推理 | 不纳入 | 未确认的推理不写入最终文档 |

### 冲突处理

- D-S2 和 D-S3 的结果如果矛盾（如 JD 分析认为"学校不重要"但主管简历推理认为"偏好名校"），以 **HR 的最终确认为准**
- 矛盾本身也有价值——记录在"风险提醒"中，说明 JD 与实际偏好的偏差

### 综合文档结构

`comprehensive-requirements.md` 按以下 7 个 section 组织：

1. **岗位画像**：岗位基本信息、类型判定、核心使命
2. **刚需条件**：硬性过滤，Module C 直接使用
3. **等效替代组**：以"组"为单位，组内 OR 逻辑
4. **次要条件**：软性评分，权重中
5. **加分项**：软性评分，权重低
6. **用人部门偏好**：来自 D-S3 的已确认推理，软性评分
7. **风险提醒**：JD 与实际需求的偏差、潜在不合理偏好、过度要求等

See file-formats.md for the complete `comprehensive-requirements.md` template.

### HR 最终确认

生成 comprehensive-requirements.md 后，展示核心摘要给 HR：

> "综合岗位需求已生成，概览如下：
> - 刚需条件 X 条（不满足则淘汰）
> - 等效替代 X 组（组内满足任一即可）
> - 次要条件 X 条 + 加分项 X 条（软性评分）
> - 用人部门偏好 X 条（来自上下文推理）
> - 风险提醒 X 条
>
> 详细内容已写入 comprehensive-requirements.md。
> 确认后，后续简历筛选将基于此文档进行。
> 如果之后需要调整，可以随时重新运行。"

### 下游集成

| 下游模块 | 使用方式 |
|---------|---------|
| **Module A (A-S5)** | 读取 comprehensive-requirements.md 的"岗位画像"和"刚需条件"，进行更精准的误分类检测。例如：JD 写"市场推广"但 comprehensive-requirements.md 分析出核心是"数据分析"→ 一个有数据分析背景但无营销经验的简历不应被标为误分类 |
| **Module B (B-S2)** | 以 comprehensive-requirements.md 为基线，分析面试官反馈与需求的偏差。例如：刚需条件没有要求"大厂经验"，但面试反馈中大厂经验的候选人全部通过 → 这就是一个有价值的偏差信号 |
| **Module C (C-S1)** | comprehensive-requirements.md 直接替代 jd.md 作为条件来源。刚需 → 硬性过滤；等效替代 → 组内 OR 的硬性过滤；次要 + 加分 + 偏好 → 软性加权评分。C-S1 的工作量大幅减少（不需要自己从原始 JD 中提取和分类条件） |

### D-S4 Completion

- Write comprehensive-requirements.md
- Append to D.log.md: 各 section 条目数、最终确认状态
- 通知 HR Module D 完成
